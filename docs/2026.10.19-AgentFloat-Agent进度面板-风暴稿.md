## 0. 方案概览（当前最优解 · 随轮次重写）

> v0.4：吸收 Round 3 的切换动线、工作台落点、L2 布局与提醒分级；L2 改为独立新做（用户明确选择）。

- **一句话定位**：AgentFloat 从「Agent 启动器」升级为「多 Agent 工作状态中枢」——用一层环境雷达看全局，用一个驾驶舱看细节，回答四个问题：**谁在跑？做到哪？还要多久？谁需要我？**
- **核心用户时刻**：同时推进 3+ 个项目时，不切换窗口也能知道全局；需要深看时，再打开详细工作台。
- **三层价值**：
  1. **可见**：把进度从聊天流里抽出来，变成稳定、可扫视的外部状态。
  2. **可算**：用步骤预估 + tokens/s + 历史同类任务校准 ETA，建立时间感。
  3. **可调度**：把「需要我介入」的会话顶上来，做注意力路由，而不只是展示进度。
- **形态（Round 1 + Round 3 定）**：L0/L1/L2 三层，逐级递进切换。
  - **L0 伴生层（自动）**：浮球旁的项目条，每个项目一行，标准五件——项目名 / n/N / 当前步 / ETA / 状态色。预计 >2 分钟或 ≥3 步时自动出现；全部结束 10 秒收起。**与现有进程面板的「运行中 Agent」显示融合**，不新增第二个悬停入口。
  - **L1 锚定快面板（点击 L0）**：贴浮球展开，显示当前项目的步骤列表、当前步、ETA、失败原因与「需要输入」提示；**承接进程面板的「中断 / 继续任务 / 聚焦窗口」能力**；不抢焦点。
  - **L2 独立工作台（手动 pin，独立新做）**：新设计的常驻置顶窗口，主从分栏——左侧项目列表（状态 + n/N + ETA），右侧当前项目完整详情（每步预估 vs 实际、会话信息、操作按钮）；可拖到副屏，位置与宽度记忆。
  - **切换动线**：L0 点项目条 → L1；L1「打开工作台」→ L2；L2 关闭回到 L0。不做多入口，不做完全可配置。
  - **过渡期说明**：现有悬停进程面板的能力逐步下沉到 L0/L1，避免「悬停面板 + 伴生层」双入口冲突；退役节奏在实施阶段确认。
- **排序（Round 1 定）**：A+C 组合——平时按用户固定顺序；等待输入 / 失败 / 完成待验收的项目临时置顶并高亮，处理完回到原位。
- **提醒分级（Round 3 定）**：明确上报的失败 / 需要输入 → 临时置顶 + 托盘通知一次（可在设置关闭）；推测的停滞（长时间无活动）→ 仅黄灯，不弹通知；「需要输入」作为协议事件补充（原型只有 fail）。
- **项目识别（Round 3 默认）**：项目名默认取 git 仓库根目录名，取不到则用工作目录名；可在 L2 改名，存为别名；重名项目按目录路径 hash 区分。
- **上报通道（Round 2 定）**：**AF 自带 CLI + 自动部署 skill 为主通道**——Agent 执行 `af progress plan/step/done/fail`，写入 `%APPDATA%/AgentFloat/progress/*.json`，AF 用文件监听实时渲染。跨 Agent、不注入插件、离线可用。
  - 二阶段增强：精简版 OpenCode 插件（复用归档的协议层与状态机，去掉显示通道），提供工具级可靠性与 `lastActivity` 停滞检测。
  - 远期：MCP server 作为标准接口；只读 `opencode.db` / dsh 状态作为零配置兜底降级。
- **上报契约（Round 2 定）**：沿用已验证的四动作 `plan / step / done / fail`（+ `stop`）；一个任务一份计划，最多 7 步，每步一行 ≤20 字；Agent 自动生成计划，用户只读；协议预留 `revision` 字段，编辑能力留到第二阶段。
- **ETA 算法（Round 2 定）**：**速度投影打底**——用已完成步骤的实际耗时推算全局速度，剩余步骤按 ETA 权重换算，每完成一步重新校准；历史同类步骤统计作为第二阶段增强。`tokens/s` 与 `lastActivity` 只当健康信号（是否还在动 / 是否停滞），不参与 ETA 计算。
- **ETA 呈现（Round 2 定）**：自适应区间——前 1~3 步给宽区间（如 `~20–60m`），过半后收紧为点估；数据不足显示「待估」，不给假精确。L1 展开显示推算依据，L2 显示每步「预估 vs 实际」。
- **MVP 假设**：以 OpenCode 为第一个验证对象，用 CLI + skill 打通「单 Agent、多项目并行」；不限死只服务 OpenCode，其它 Agent 能跑 shell 即可接入。
- **差异化假设**：dsh 的步骤栏是「单会话内的线性列表」；AF 做的是「跨项目、跨会话的全局状态层 + 注意力调度」。这是「工作站」与「插件」的分界。
- **设计约束**：L0/L1/L2 共用同一份状态模型与组件，不各写一套 UI；L2 是 L1 的扩展，不是另一个产品。

## 1. 目的与成功标准

- **目的**：为 AgentFloat 设计一个以「Agent 工作进度面板」为核心的新功能/玩法，解决多项目并行时的进度模糊、时间感缺失、状态汇报啰嗦，并提升 AF 的使用频率与不可替代性。
- **本次风暴成功标准**：产出一份**可评审的方案框架**——方向、信息架构、关键取舍、技术路径、MVP 边界与验证指标清楚；不要求执行级排期与代码。
- **节奏**：每轮 2~4 题快问快答 + 自由输入；关节节点给全览；收束由用户手动触发。
- **明确不在本次范围**：直接写代码、改项目源码、排期承诺。

## 2. 初始想法（畅谈整理稿）

> 用户畅谈原文整理（2026-10-19），尚未逐条确认。

1. **起点**：使用 dsh 时，Agent 有时会出现工作步骤条目，能一栏显示工作现状和后续内容，但仍不够直观。
2. **迁移后的落差**：主要工作平台迁到 OpenCode 后，没有对应的进度插件；尝试自制插件，显示效果很一般。
3. **灵光**：把进度条放到 AgentFloat 上——既升华 AF「Agent 工作站」的概念，又真正解决工作内容模糊、进度模糊的问题。
4. **ADHD 视角**：人在用 Agent 同时推进很多项目时，注意力被分散，无法直观了解 Agent 的工作线路与现状；需要外部化的「工作记忆」。
5. **痛点 1 · 多项目并列**：支持同步推进多个项目的进度并列显示。
6. **痛点 2 · 时间感**：根据 Agent 的 tokens/s 和以往工作经验，推测每个环节大致需要的时间，让多会话控制更有时间概念和规划性。
7. **痛点 3 · 省 token 且更直观**：省去 Agent 在会话里啰嗦项目现状、未来预期的内容；这些内容浪费 token、不直观、充满黑话。希望通过客制化 skills 搭配，把进度汇报搬到 AF，让 Agent 实时操作浮窗上的进度显示面板。
8. **痛点 4 · 产品价值**：丰富 AF 功能，提高使用频率与依赖性。

## 4. 快问快答实录

### Round 1 · 形态与信息层级（2026-10-19）

**Q1 主形态：工作状态层住在哪里？**
- 选项：A 浮球伴生双层 / B 独立悬浮工作台 / C 菜单里的工作台页 / D 贴 OpenCode 窗口
- 回答：**A+B 都要**。A 显示最简单的进度；B 显示最详细的版本；最好能自由灵活切换。
- 结论：不是二选一，而是 **L0 伴生层（A）+ L1 锚定快面板 + L2 独立工作台（B）** 三层。L0 负责环境感知，L2 负责深度查看，L1 是两者之间的点击展开态。

**Q2 出现策略：什么时候出现？**
- 选项：A 值得看才出现 / B 仅多项目时出现 / C 常驻空态 / D 手动 pin
- 回答：**伴生层按 A 自动出现；独立工作台由用户手动 pin。**
- 结论：L0 用「预计 >2 分钟或 ≥3 步」做阈值，全部结束 10 秒收起；L2 不自动弹，由用户固定。

**Q3 收起态信息密度：一行放多少？**
- 选项：A 极简三件 / B 标准五件 / C 数据流七件
- 回答：**B 标准五件。**
- 结论：L0 每行固定「项目名 + n/N + 当前步 + ETA + 状态色」；tokens/s、心跳等放入 L1/L2 或悬停提示。

**Q4 多项目排序：谁在前面？**
- 选项：A 需要我优先 / B 最近活跃优先 / C 用户固定顺序 / D 项目优先级标签
- 回答：**A+C 组合。**
- 结论：默认固定顺序；等待输入 / 失败 / 完成待验收临时置顶并高亮，处理完回原位。

**Round 1 脑洞（待后续验证）**
- 把「进度条」改成「红绿灯」：绿灯在跑、黄灯等你、红灯卡住。
- 不需要你的项目淡出为 3px 呼吸线，只有需要你的项目展开。
- 时间账本：记录 ETA vs 实际耗时，形成个人速度模型。

### Round 2 · 上报通道与 ETA（2026-10-19）

**Q1 上报通道：第一版主通道用哪条？**
- 选项：A CLI + skill / B 精简版 OpenCode 插件 / C MCP server / D 只读会话数据兜底
- 回答：**A CLI + skill 主通道。**
- 结论：AF 自带 `af` 命令并自动把 skill 部署到各 Agent 的 skills 目录；进度写入本地状态目录，AF 文件监听渲染。OpenCode 插件作为二阶段增强，MCP 远期，只读数据只做兜底。

**Q2 上报契约：计划谁定、能不能改？**
- 选项：A 原型四动作、用户只读 / B 首版可编辑 / C 用户先定模板 / D 自动 + 可接管
- 回答：**A 原型四动作，用户只读。**
- 结论：沿用 `plan / step / done / fail / stop`；≤7 步、一行 note；协议预留 `revision` 字段，编辑能力留到第二阶段。

**Q3 ETA 算法：用什么算？**
- 选项：B 速度投影 / B→D 投影 + 历史统计 / A 原始预估累加 / C tokens/s
- 回答：**B 速度投影打底。**
- 结论：用已完成步骤的实际耗时推算全局速度，剩余步骤按 ETA 权重换算；历史统计后置；`tokens/s` 与 `lastActivity` 仅作健康信号。

**Q4 ETA 呈现：怎么显示？**
- 选项：A 自适应区间 / D 分层组合 / B 点估 / C 只报步数
- 回答：**A 自适应区间。**
- 结论：早期宽区间、过半收紧为点估、数据不足显示「待估」；L1 展开显示推算依据，L2 显示每步预估 vs 实际。

**Round 2 关键实证（来自原型与归档）**
- 原型状态模型（本机 `opencode.db` 的 kv 中仍留有 4 组真实记录）：`status / steps[{name, etaMin, status, note, startedAt, endedAt, reason}] / current / startedAt / updatedAt / title / lastActivity / summary`。
- 原型代码与 `progress-protocol` skill 在 `C:\AIAgentBase\_archive\2026-10-19-OpenCode进度条插件\`，协议层、状态机、ETA 校准、通知都可复用。
- 反例：5 步各 45 分钟时标题显示「剩 3h19m」——原始预估累加会放大误差，这正是速度投影要解决的问题。

**Round 2 脑洞（待后续验证）**
- 停滞检测比 ETA 更重要：`lastActivity` 超过阈值 → 黄灯 + 「可能在等你输入」。
- 计划复用：同类任务复用上次的步骤与 ETA 模板。
- 时间账本反向用法：汇总各项目剩余 ETA，回答「Agent 队列今天还有多久」。

### Round 3 · 切换动线、工作台落点与提醒（2026-10-19）

**Q1 三层怎么切换？**
- 选项：A 逐级递进 / B 直达工作台 / C 左键右键分工 / D 完全可配置
- 回答：**A 逐级递进。**
- 结论：L0 点项目条 → L1 快面板 → L1「打开工作台」→ L2；L2 关闭回 L0。不做多入口、不做配置项。

**Q2 L2 工作台建在哪？**
- 选项：A 升级现有进程面板 / B 新建独立工作台 / C 控制与进度分家 / D 只做在 Web 控制台
- 回答：**伴生层和快面板与现有进程面板融合；工作台要做一个独立的。**
- 结论（偏离 Agent 推荐，记录在案）：L0/L1 承接进程面板的「中断 / 继续任务 / 聚焦窗口」能力（能力下沉、不新增悬停入口）；**L2 独立新做**，按驾驶舱标准设计主从分栏窗口。过渡期需处理旧悬停面板的去留，避免双入口冲突。

**Q3 L2 内部怎么排多项目？**
- 选项：A 主从分栏 / B 纵向堆叠卡 / C 看板 / D 焦点模式
- 回答：**A 主从分栏。**
- 结论：左侧项目列表（状态 + n/N + ETA）、右侧当前项目详情（每步预估 vs 实际 + 操作）；窄窗降级与看板留作后续皮肤，一套数据多套渲染。

**Q4 什么时候提醒？**
- 选项：A 分级提醒 / B 只用面板黄灯 / C 全量通知 / D 不检测停滞
- 回答：**A 分级提醒。**
- 结论：明确上报的失败 / 需要输入 → 置顶 + 托盘通知一次（可关）；推测的停滞 → 仅黄灯。协议需补「需要输入」事件。

**Round 3 关键实证与默认项**
- 现有 `ui/process_panel.py` 已具备：卡片、PID、运行时长、最近活动、软中断/结束进程树、继续任务、聚焦窗口、空态、缩放与透明度——L0/L1 的能力下沉有现成实现可复用。
- 项目识别默认：git 仓库根目录名优先，fallback 工作目录名；L2 可改名；重名按路径 hash 区分。

**Round 3 脑洞（待后续验证）**
- 「等我」队列：把需要输入/失败的会话聚成一条队列，处理完自动消失。
- 免打扰时段：专注时收进浮球，只累计「需要我」计数，结束后一次性呈现。
- 每日站会视图：早上打开 L2 看到昨天未完成步骤 + 今天各项目计划。

## 5. 未决问题 · 风险 · 旁支灵感

### 5.1 未决问题

- **旧进程面板的退役节奏**：能力下沉到 L0/L1 后，悬停面板何时下线？过渡期如何避免「悬停面板 + 伴生层」双入口与手势冲突？
- **L2 窗口细节**：默认尺寸、位置与宽度记忆、多屏策略、是否置顶但不抢焦点、缩放与透明度是否沿用进程面板那套。
- **「需要输入」事件**：原型只有 `fail`；需要补 `need-input` 事件（或 fail 的子类型），并定义它何时自动解除（用户继续任务后）。
- **信息分工细节**：L0 的「当前步」摘要由 Agent 上报还是 AF 截断？L2 的步骤编辑能力何时开放（协议已留 revision）？
- **skill 部署**：AF 自动部署到哪些 Agent 的 skills 目录？与已有 skill（本机 20 个）的版本更新与冲突如何管理？
- **状态生命周期**：会话结束/中断/崩溃后状态保留多久？多实例与状态目录清理策略？
- **停滞检测阈值**：多久无活动算停滞（建议 3–5 分钟起步）？是否按任务类型自适应？恢复活动后如何优雅转回正常态？
- **验证**：用什么指标判断它真的提升了频率与依赖？打开次数、任务覆盖率、ETA 命中率、状态汇报 token 降幅？

### 5.2 风险

- **三层过度设计风险**：L0/L1/L2 如果各写一套 UI 与交互，会变成三个半成品；L2 虽是独立新做，但必须共用同一份状态模型与令牌，且不得复制进程控制逻辑。
- **双入口过渡风险**：L0/L1 与旧悬停进程面板并存期间，用户可能看到两处「运行中的 Agent」；需要明确退役顺序，避免手势冲突与信任流失。
- **L2 独立新做的工作量**：独立工作台意味着新窗口、新布局、新交互都要从头验证；需在 MVP 里控制范围（先只读 + 基础操作）。
- **噪音风险**：常驻面板变成视觉负担，尤其多项目时；收起态必须极度克制。
- **假精确风险**：ETA 偏差大反而破坏信任；应显示区间/置信度，并允许「不估」。
- **协议耦合风险**：显示端只依赖本地状态格式；OpenCode 插件与只读适配器都退化为可替换的适配层，升级坏了也不影响主链路。
- **漏报风险**：CLI 通道依赖模型纪律，漏报一步会让进度看起来卡住；需要「停滞检测」与「状态超时降级」兜底，而不是只信任上报。
- **CLI 开销风险**：每步一次进程启动，若 CLI 启动慢（&gt;300ms），累积起来会拖慢 Agent 节奏；需要做轻量入口或常驻管道。
- **token 反噬**：如果每次上报都要 Agent 写长 JSON 或调用重工具，省下的叙述 token 会被吃掉。
- **隐私风险**：步骤名可能包含项目/客户信息；默认只存本机、可一键清除。
- **性能风险**：多会话高频更新 + Qt 重绘；需要节流、批处理与静息降频。

### 5.3 旁支灵感

- **「需要我」队列**：把「等你输入 / 失败 / 完成待验收」的会话置顶，像交通管制一样分配注意力。
- **工作日志自动成稿**：一天结束把各项目步骤流导出为「今日工作摘要」，替代手工记录。
- **时间预算**：启动任务前先填「这一步预算 10 分钟」，超时变色，训练时间感。
- **交接模式**：把当前进度面板一键导出为 HANDOFF，供下一个会话/明天接上。
- **历史同类步骤库**：按任务类型（改前端/跑测试/写文档）沉淀实际耗时，ETA 越用越准。
