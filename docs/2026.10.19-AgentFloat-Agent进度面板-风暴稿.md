## 0. 方案概览（最终版）

### 0.1 一句话定位

AgentFloat 从「Agent 启动器」升级为「**多 Agent 工作状态中枢**」：用一层环境雷达看全局，用一个独立驾驶舱看细节，回答四个问题——**谁在跑？做到哪？还要多久？谁需要我？**

### 0.2 核心用户时刻与三层价值

- **用户时刻**：同时推进 3+ 个项目（AF / ProjectDock / VIDAR 各一个会话）时，不切换窗口也能掌握全局；需要深看或干预时，再打开工作台。
- **三层价值**：
  1. **可见**：把进度从聊天流里抽出来，变成稳定、可扫视的外部状态。
  2. **可算**：速度投影 + 自适应区间，建立真实的时间感。
  3. **可调度**：把「需要我介入」的会话顶上来，做注意力路由。

### 0.3 形态：三层信息架构（L0 / L1 / L2）

| 层 | 名称 | 何时出现 | 显示什么 | 定位 |
|---|---|---|---|---|
| L0 | 伴生层 | 预计 &gt;2 分钟或 ≥3 步时自动出现；全部结束 10 秒收起 | 每项目一行**标准五件**：项目名 / n/N / 当前步 / ETA / 状态色 | 环境雷达，零点击可见 |
| L1 | 锚定快面板 | 点击 L0 项目条展开，贴浮球 | 当前项目步骤列表、当前步、ETA、失败原因与「需要输入」；承接**中断 / 继续任务 / 聚焦窗口**；不抢焦点 | 轻量查看 + 就地干预 |
| L2 | 独立工作台 | 用户手动 pin 常驻（独立新做） | 主从分栏：左侧项目列表（状态 + n/N + ETA），右侧当前项目完整详情（每步预估 vs 实际、会话信息、操作按钮）；可拖副屏，位置与宽度记忆 | 深度工作与调度 |

- **切换动线**：L0 点项目条 → L1 → 「打开工作台」→ L2；L2 关闭回 L0。不做多入口、不做配置项。
- **排序**：平时按用户固定顺序；等待输入 / 失败 / 完成待验收临时置顶并高亮，处理完回原位。
- **能力来源**：L0/L1 与现有进程面板（`ui/process_panel.py`）**融合**，中断/继续/聚焦等能力下沉，不新增第二个悬停入口；**L2 独立新做**（用户明确选择，偏离「升级进程面板」的推荐）。过渡期需处理旧悬停面板的退役，避免双入口冲突。
- **设计约束**：三层共用同一份状态模型与设计令牌；L2 不复制进程控制逻辑。

### 0.4 数据与协议（v1.2 修正：M1 三件套）

- **分层原则**：**协议只有一份，通道可以有多个。** MCP 是「手」、skill 是「脑」、CLI 是「保底」、OpenCode 插件是「加速器」；显示层永远只读同一份状态。
- **M1 三件套（用户选择，修正原计划）**：CLI + skill + MCP 同版本交付，共享同一个写入内核。
  - **MCP**：AF 安装包附带 `af-mcp`（stdio 小进程）；只暴露**一个** `progress` 工具，`action` 枚举 `plan / step / done / fail / need_input / next`；`step` 的返回值带「下一步 + 校准后 ETA」，充当 Agent 的外部工作记忆。
  - **CLI**：`af progress plan/step/done/fail`，供不支持 MCP 或未配置 MCP 的 Agent 使用；与 MCP 写同一份状态。
  - **Skill**：一份 `progress-protocol`，规定启用条件、每步一行、不重复播报；**优先调用 MCP 工具，不可用时回退 CLI**；AF 部署时只替换命令绝对路径。
- **状态**：写入 `%APPDATA%/AgentFloat/progress/<sessionID>.json`（原子写，带 `project` 字段）；AF 用 `QFileSystemWatcher` 监听渲染。**AF 未运行时写入也不丢**，启动后自动读回；每个会话一个文件，天然支持多会话并发。
- **契约**（沿用已验证的原型）：
  - 一个任务一份计划，最多 7 步，每步一行 ≤20 字。
  - 状态模型：`project / sessionID / status / steps[{name, etaMin, status, note, startedAt, endedAt, reason}] / current / startedAt / updatedAt / lastActivity / summary`。
  - Agent 自动生成计划，**用户只读**；协议预留 `revision` 字段，编辑能力留到第二阶段。
- **增强与兜底**：
  - 二阶段：精简版 OpenCode 插件（复用归档的 `protocol.ts / state.ts / tool.ts`，去掉显示通道），提供工具级可靠性与 `lastActivity` 停滞检测。
  - 可选增强：AF 启动 Agent 时注入一段短协议（只覆盖 AF 启动的会话），作为零安装路径。
  - 兜底：只读 `opencode.db` / dsh 状态——零配置降级，拿不到计划与 ETA 时只显示「活跃 / 停滞」，**绝不伪造步骤**。

### 0.5 ETA：算得诚实

- **算法**：**速度投影打底**——用已完成步骤的实际耗时推算全局速度，剩余步骤按 ETA 权重换算，每完成一步重新校准；历史同类步骤统计作为第二阶段增强。
- **健康信号**：`tokens/s` 与 `lastActivity` 只用于「还在不在动 / 是否停滞」，不参与 ETA 计算。
- **呈现**：自适应区间——前 1~3 步给宽区间（如 `~20–60m`），过半后收紧为点估；数据不足显示「待估」，不给假精确。L1 展开显示推算依据，L2 显示每步「预估 vs 实际」。
- **反例记录**：原型中 5 步各 45 分钟 → 标题显示「剩 3h19m」，正是「原始预估累加」被否决的原因。

### 0.6 调度与提醒

- **提醒分级**：
  - 明确上报的**失败 / 需要输入** → 临时置顶 + 托盘通知一次（可在设置关闭）。
  - **推测的停滞**（长时间无活动）→ 仅黄灯 + 一行原因，不弹通知；恢复活动自动转回。
- **项目识别**：项目名默认取 git 仓库根目录名，取不到则用工作目录名；可在 L2 改名（存别名）；重名项目按目录路径 hash 区分。

### 0.7 MVP 台阶（v1.2：M1 三件套）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M1 协议闭环（三件套）** | CLI + skill + MCP 同版交付；状态目录 + 文件监听；L0 标准五件 + L1 快面板（含中断/继续/聚焦）+ 分级提醒 | OpenCode 里跑 3 个并行任务，L0 实时显示，卡住能就地处理；MCP 与 CLI 写出的状态一致 |
| **M2 独立工作台** | L2 主从分栏 + 每步预估 vs 实际 + 项目别名 + 窗口位置记忆 + pin 常驻 | 多项目场景下，信息与操作不用切窗口 |
| **M3 增强与开放** | 历史速度模型 + OpenCode 精简插件 + 只读兜底 + 计划模板复用 + 启动器注入（可选）+ **任务栏按钮进度（轮播，M3 候选）** | ETA 越用越准；其它 Agent 可无痛接入；系统面可选 |

> **M1 实施顺序（降风险）**：CLI 内核 → MCP 适配（复用同一内核）→ skill → L0/L1。三件套同里程碑交付，但不三线并行。

### 0.8 验证与上线节奏

- **试点场景**：OpenCode 单 Agent、多项目日常——用真实工作跑一周（建议 AF / ProjectDock / VIDAR 三会话并行）。
- **成功指标（Round 4 选择）**：
  1. **频率**：≥5 次/天被动扫到 L0、≥1 次/天主动打开 L1/L2。
  2. **信任**：实际完成时间落在 ETA 区间内 ≥70%；最坏偏差 ≤2×。
  - 次要/隔期自评：一周后「关掉它会不会不习惯」；状态汇报类输出字数主观下降。
- **上线节奏（用户自定义）**：debug 版跑通 → 测试版自用 + 持续迭代 → **用户主观觉得很好**后转正式版。默认期间不打 tag / 不发 Release / 不同步官网。

### 0.9 反目标（第一版明确不做）

计划编辑与拖拽排序 · 历史回放与数据看板 · 贴 OpenCode 窗口的像素级进度条 · 多 Agent 自动接入（只读兜底除外）· 云同步 · 声音提醒 · 暂停/跳过/重排步骤 · 会话正文入库 · 任务栏/系统级集成（M3 候选，已评估；不进 M1/M2）。

### 0.10 关键风险与对策（速览）

| 风险 | 对策 |
|---|---|
| 三层 UI 各写一套变成三个半成品 | 共用状态模型与令牌；L2 不复制控制逻辑 |
| 旧悬停进程面板与新 L0/L1 双入口 | 明确退役顺序；过渡期避免同时出现两处「运行中」 |
| CLI 每步一次进程启动拖慢节奏 | 轻量入口（目标 &lt;150ms）或常驻管道；必要时转插件通道 |
| 三通道并行维护导致行为不一致 | 三个适配器只做薄封装，共用同一写入内核与同一份测试样本；禁止各自实现状态机 |
| MCP 客户端配置门槛高、各客户端格式不同 | 提供一键注册命令/配置片段；未配置时 skill 自动回退 CLI，不阻塞使用 |
| MCP 单工具 schema 演进导致兼容问题 | 状态 JSON 带 `version`；工具只增字段不破坏旧字段；客户端不匹配时降级 CLI |
| 任务栏按钮需要新增可见窗口 | 用独立「任务栏代理窗口」承载 ITaskbarList3；提供设置可关闭；接受 Alt+Tab 多一项，或先验证 `ITaskbarList::AddTab` 能否免 Alt+Tab |
| 轮播把「需要我」的项目转走 | 需要我优先并 pin，直到用户处理；角标/进度状态同时变琥珀/红色；悬停暂停轮播 |
| 模型漏报导致进度停住 | 停滞检测 + 状态超时降级；不伪造步骤 |
| ETA 假精确破坏信任 | 自适应区间 + 命中率验收；数据不足显示「待估」 |
| 噪音/通知疲劳 | L0 收起态极度克制；只有明确「需要我」才弹通知 |
| 隐私（步骤名含项目/客户信息） | 只存本机、可一键清除、不入库会话正文 |

## 1. 目的与成功标准

- **目的**：为 AgentFloat 设计一个以「Agent 工作进度面板」为核心的新功能/玩法，解决多项目并行时的进度模糊、时间感缺失、状态汇报啰嗦，并提升 AF 的使用频率与不可替代性。
- **本次风暴成功标准**：产出一份**可评审的方案框架**——方向、信息架构、关键取舍、技术路径、MVP 边界与验证指标清楚；不要求执行级排期与代码。
- **节奏**：每轮 2~4 题快问快答 + 自由输入；关节节点给全览；收束由用户手动触发。
- **明确不在本次范围**：直接写代码、改项目源码、排期承诺。

## 2. 初始想法（畅谈整理稿）

> 用户畅谈原文整理（2026-10-19）。

1. **起点**：使用 dsh 时，Agent 有时会出现工作步骤条目，能一栏显示工作现状和后续内容，但仍不够直观。
2. **迁移后的落差**：主要工作平台迁到 OpenCode 后，没有对应的进度插件；尝试自制插件，显示效果很一般。
3. **灵光**：把进度条放到 AgentFloat 上——既升华 AF「Agent 工作站」的概念，又真正解决工作内容模糊、进度模糊的问题。
4. **ADHD 视角**：人在用 Agent 同时推进很多项目时，注意力被分散，无法直观了解 Agent 的工作线路与现状；需要外部化的「工作记忆」。
5. **痛点 1 · 多项目并列**：支持同步推进多个项目的进度并列显示。
6. **痛点 2 · 时间感**：根据 Agent 的 tokens/s 和以往工作经验，推测每个环节大致需要的时间，让多会话控制更有时间概念和规划性。
7. **痛点 3 · 省 token 且更直观**：省去 Agent 在会话里啰嗦项目现状、未来预期的内容；这些内容浪费 token、不直观、充满黑话。希望通过客制化 skills 搭配，把进度汇报搬到 AF，让 Agent 实时操作浮窗上的进度显示面板。
8. **痛点 4 · 产品价值**：丰富 AF 功能，提高使用频率与依赖性。

### Round 1 · 形态与信息层级（2026-10-19）

### Round 2 · 上报通道与 ETA（2026-10-19）

**Q1 上报通道：第一版主通道用哪条？**

**Q2 上报契约：计划谁定、能不能改？**

**Q3 ETA 算法：用什么算？**

**Q4 ETA 呈现：怎么显示？**

- 结论：早期宽区间、过半收紧为点估、数据不足显示「待估」；L1 展开显示推算依据，L2 显示每步预估 vs 实际。

**Q4 skill 怎么处理多种通道？**
- 选项：A 一份 skill 内部回退 / B 按客户端生成变体 / C skill 只讲纪律 / D 不做 skill
- 回答：**A 一份 skill，内部回退。**

**Round 5 实现要点（新增）**
- MCP 服务器形态：**stdio 小进程 `af-mcp`**，随 AF 安装包提供；不依赖 AF 常驻，写入状态目录即可；AF 启动后读回。
- 状态文件：`progress/<sessionID>.json`，每会话一个文件，带 `project` 字段；AF 按 project 分组渲染。
- 工具返回示例：`{ok, current, total, next, eta_range, hint}`——短、结构化、可直接指导下一步。
- 「省 token」的边界：结构化上报本身不省很多，真正省的是不再写长篇状态叙述；skill 必须禁止「调用工具后再解释一遍」。

## 5. 未决问题 · 风险 · 旁支灵感

### 5.1 未决问题（实施期需要定）

- **旧进程面板的退役节奏**：能力下沉到 L0/L1 后，悬停面板何时下线？过渡期如何避免双入口与手势冲突？
- **CLI 形态与性能**：独立轻量 exe 还是复用 Python？目标是启动 &lt;150ms；是否需要常驻管道或本地 HTTP？
- **MCP 部署方式**：`af-mcp` 如何注册到 OpenCode / Claude Code / Codex？AF 自动改配置（需用户同意）还是给出一键命令/配置片段？
- **MCP 进程与并发**：每个客户端各起一个 stdio 进程，如何避免同会话并发写冲突？需要文件锁还是「最后写入者胜」+ `updatedAt` 校验？
- **三通道一致性**：CLI / MCP / 插件写出的状态必须完全一致；需要一份共享的协议测试样例与回归清单。
- **schema 版本化**：状态 JSON 的 `version` 如何演进？MCP 工具字段只增不删的兼容策略。
- **启动器注入**：各 Agent 是否支持追加系统提示/环境变量？只覆盖 AF 启动的会话，是否值得做。
- **任务栏代理窗口**：用独立可见窗口还是 `ITaskbarList::AddTab`？前者必然进 Alt+Tab，后者能否保留 `WS_EX_TOOLWINDOW` 需实测；窗口标题/图标/点击行为怎么定。
- **轮播规则**：间隔几秒？悬停是否暂停？「需要我」项目 pin 多久、处理完如何归位？项目多时是否只轮播运行中的？
- **任务栏状态表达**：进度条颜色/状态（正常/暂停/错误）、overlay 角标内容、`SetThumbnailTooltip` 文案、动态标题是否可接受。
- **任务栏边界**：多显示器任务栏、自动隐藏、DPI 缩放、全屏应用、任务栏重启（Explorer 崩溃）后的重挂。
- **开关与降级**：是否提供「不在任务栏显示进度」设置；代理窗口创建失败时是否自动降级到托盘角标。
- **「需要输入」事件**：作为独立事件还是 fail 的子类型？用户点「继续任务」后如何自动解除？
- **L2 窗口细节**：默认尺寸、位置与宽度记忆、多屏策略、置顶但不抢焦点、缩放与透明度是否沿用进程面板。
- **skill 部署**：自动部署到哪些 Agent 的 skills 目录？与已有 skill（本机约 20 个）的版本更新与冲突如何管理？
- **状态生命周期**：会话结束/中断/崩溃后状态保留多久？多实例与状态目录清理策略？
- **停滞检测阈值**：建议 3–5 分钟起步；是否按任务类型自适应；恢复活动后如何优雅转回。
- **信息分工细节**：L0 的「当前步」摘要由 Agent 上报还是 AF 截断？L2 步骤编辑何时开放（协议已留 revision）。
- **只读兜底**：`opencode.db` 并发读的实现与降级策略；格式变化时的失效保护。
- **历史统计归类**：步骤名如何归类到任务类型（关键词/向量/手动标签）？

### 5.2 风险

- **三层过度设计风险**：L0/L1/L2 各写一套 UI 会变成三个半成品；L2 虽独立新做，但必须共用状态模型与令牌，且不得复制进程控制逻辑。
- **双入口过渡风险**：L0/L1 与旧悬停进程面板并存期间，用户可能看到两处「运行中的 Agent」；需要明确退役顺序。
- **L2 独立新做的工作量**：新窗口、新布局、新交互都要从头验证；MVP 里先只读 + 基础操作，控制范围。
- **噪音风险**：常驻面板变成视觉负担；收起态必须极度克制。
- **假精确风险**：ETA 偏差大破坏信任；用区间/置信度，允许「不估」。
- **协议耦合风险**：显示端只依赖本地状态格式；OpenCode 插件与只读适配器都是可替换的适配层。
- **漏报风险**：CLI 通道依赖模型纪律；用停滞检测与超时降级兜底，不伪造步骤。
- **CLI 开销风险**：每步一次进程启动；需要轻量入口或常驻管道。
- **token 反噬**：上报本身要足够短，否则省下的叙述 token 被吃掉。主价值是可读性而非省 token。
- **隐私风险**：步骤名可能含项目/客户信息；只存本机、可一键清除。
- **性能风险**：多会话高频更新 + Qt 重绘；需要节流、批处理与静息降频。

### 5.3 旁支灵感

- **「需要我」队列**：把「等你输入 / 失败 / 完成待验收」的会话聚成队列，像交通管制一样分配注意力。
- **工作日志自动成稿**：一天结束把各项目步骤流导出为「今日工作摘要」。
- **时间预算**：启动任务前先填「这一步预算 10 分钟」，超时变色，训练时间感。
- **交接模式**：把当前进度面板一键导出为 HANDOFF，供下一个会话/明天接上。
- **历史同类步骤库**：按任务类型沉淀实际耗时，ETA 越用越准。
- **免打扰时段**：专注时收进浮球，只累计「需要我」计数，结束后一次性呈现。
- **每日站会视图**：早上打开 L2，看到昨天遗留 + 今天计划的交接班视图。

## 8. M1 实施拆解（可开工）

> 目标：把 M1 三件套拆成可独立验收的切片；不改变已定架构。结构图沿用 §7.1 的架构图与时序图，本轮不新增图。

### 8.1 三条硬规则

1. **CLI / MCP 不 import PyQt5**：否则每次上报都要拉起 GUI 运行时，启动慢、打包大、测试难。`model / store / eta / protocol` 必须是纯 Python。
2. **状态写入只有一个入口**：`store.py`。CLI、MCP、未来的插件都调用它；禁止各自实现状态机或原子写。
3. **UI 只读快照**：L0/L1/L2 通过 `ProgressService` 拿 `snapshot`，不直接读文件、不推断状态。

### 8.2 模块与文件

| 模块 | 路径 | 职责 | 依赖 |
|---|---|---|---|
| 模型 | `services/progress/model.py` | 状态/步骤 dataclass、schema 校验、状态迁移规则 | 纯 Python |
| 存储 | `services/progress/store.py` | 状态目录、文件命名、原子写、锁、读取/列出/清理 | 纯 Python |
| ETA | `services/progress/eta.py` | 速度投影、区间、置信度、格式化 | 纯 Python |
| 协议分派 | `services/progress/protocol.py` | action → store/eta 的统一执行，CLI 与 MCP 共用 | 纯 Python |
| CLI | `services/progress/cli.py` + `scripts/af_cli.py` | `af progress ...` / `af mcp` 入口 | 纯 Python |
| MCP | `services/progress/mcp_server.py` | stdio MCP server，单工具 `progress` | 纯 Python |
| Skill 部署 | `services/progress/deploy.py` | 写 `progress-protocol/SKILL.md`、版本/哈希标记、冲突跳过 | 纯 Python |
| 监听桥 | `ui/progress_watcher.py` | `QFileSystemWatcher` + 防抖 + 轮询兜底 → `ProgressService` | PyQt5 |
| 服务 | `services/progress/service.py` | 聚合快照、排序、阈值、通知去重 | PyQt5 仅信号部分 |

| 测试 | `tests/test_progress_*.py` | 模型/存储/ETA/CLI/MCP/一致性/UI 冒烟 | pytest |

### 8.3 状态协议 v2

JSON 字段沿用原型的 camelCase，避免重写已验证的数据形状；只新增 `project` / `projectId` / `agent` / `revision` / `need_input`。

```json
{
  "version": 2,
  "project": "AgentFloat",
  "projectId": "9f52ff6fe9e3",
  "sessionId": "ses_f0d708aa1ffeCo83pG2RLjnZ3f",
  "agent": "opencode",
  "title": "开发-AgentFloat开发主力",
  "status": "running",
  "steps": [
    {
      "name": "改导出层",
      "etaMin": 20,
      "status": "running",
      "note": "拆 renderer",
      "startedAt": 1792411865060
    },
    {
      "name": "补回归用例",
      "etaMin": 10,
      "status": "pending"
    }
  ],
  "current": 0,
  "startedAt": 1792411857154,
  "updatedAt": 1792411865060,
  "lastActivity": { "tool": "browser_preview", "at": 1792412362817 },
  "summary": "",
  "revision": 3
}
```

**状态枚举**：`running / done / failed / need_input / stopped`；步骤状态：`pending / running / done / failed / skipped`。

**文件命名与解析**：
- `progress/<sessionKey>.json`；`sessionKey` 优先用 `sessionId`，没有则用 `<projectId>__<cwdHash>`。
- `plan` 创建或覆盖当前 key；`step/next/done/fail` 默认解析该项目+cwd 下最新的 `running` 文件。
- 若同一项目+cwd 有多个 `running` 文件且未指定 `--session`，返回歧义错误（退出码 3），要求显式 `--session`。
- 项目名默认取 git 根目录名，取不到用 cwd 名；`projectId` 为 `sha1(gitRoot 或 cwd)[:12]`。

**写入规则**：
- `tempfile` + `os.replace` 原子写；
- 写入前比较 `revision`，不一致则重新读取（乐观锁）；高并发时用 `.lock` 文件 + 200ms 重试，超时退出码 4；
- 状态目录 `config_dir()/progress`；开发模式下为项目根 `progress/`，加入 `.gitignore`。

### 8.4 CLI 接口

```bash
# 计划（3–7 步；eta 可省略）
af progress plan --project AgentFloat --steps "改导出层|补回归用例|跑测试" --eta 20,10,5
# 推进（index 从 1 开始；note ≤20 字）
af progress step --project AgentFloat --index 2 --note "补回归用例"
# 取下一步（供 Agent 外置计划）
af progress next --project AgentFloat
# 收尾 / 失败 / 等待输入
af progress done --project AgentFloat --summary "测试全过"
af progress fail --project AgentFloat --reason "依赖缺失 xyz"
af progress need-input --project AgentFloat --reason "是否覆盖旧产物？"
# 调试
af progress dump --project AgentFloat
```

- 默认输出一行人类可读文本；`--json` 输出结构化结果。
- 退出码：`0` 成功；`2` 参数/校验错误；`3` 无活动计划或歧义；`4` 状态锁超时。
- `--session` 可选；不传则按项目+cwd 解析。
- `af mcp` 是同一个 exe 的子命令，用于 stdio MCP。

### 8.5 MCP 接口

- **形态**：`af mcp` 启动 stdio server；不依赖 AF 常驻；直接调用 `protocol.py` 写状态目录。
- **工具**：只暴露一个 `progress`，`action` 枚举 `plan / step / done / fail / need_input / next`。
- **返回**：
  ```json
  { "ok": true, "current": 3, "total": 7, "next": "补回归用例", "eta_range": "8–12m", "needs": null }
  ```
- **边界**：不接受任意文件路径；只接受 project/session/step 字段；输入长度与步数上限与 CLI 一致；无网络监听。
- **注册**：`af mcp-config --client opencode|claude|codex` 打印配置片段；M1 **不自动改客户端配置**，由用户在设置页复制或手动粘贴。MCP 不可用时 skill 回退 CLI。

### 8.6 Skill 契约

- 文件：`progress-protocol/SKILL.md`，目标 ≤400 字；模板内用 `{{AF_CLI}}` 占位，部署时替换为实际命令。
- 必写四条：
  1. 启用条件：≥3 步或 >2 分钟；单步小修/问答/纯查询不启用。
  2. 动作映射：plan → step → done/fail/need_input；需要下一步时用 next。
  3. 纪律：一行 ≤20 字、不重复播报、不写长篇总结、不伪造步骤。
  4. 通道：优先 MCP 工具 `progress`；不可用执行 `{{AF_CLI}} progress ...`。
- 部署：`deploy.py` 复用 `services/skills/scanner.py::default_skill_roots()`；只写入已存在的根目录；写 `.agentfloat-skill.json`（版本+哈希）；非本技能拥有的同名目录跳过并记日志；设置项可关闭自动部署。

### 8.7 UI 接入

- **ProgressService**：在 `app.py` 创建，连接 `ProgressWatcher`，发出 `snapshotChanged(list)`；排序规则：`need_input/failed` 优先 → 用户固定顺序 → 最近更新。
- **L0**：`Qt.Tool | FramelessWindowHint | WindowStaysOnTopHint | WA_ShowWithoutActivating`；行高 30px；最多 5 行，超出显示 `+N`；位置贴浮球并自动选侧；点击行打开 L1；全部结束 10 秒后收起。
- **L1**：复用 `panel_kit.PanelShell`；步骤列表（✓ / ▶ / ○ / ⚠）、ETA 区间、底部按钮「继续任务 / 中断 / 聚焦窗口 / 打开工作台」；`need_input` 时顶部显示一行原因。
- **阈值**：`plan` 的步骤 ≥3 或总 ETA >2 分钟才让 L0 出现；否则只记状态、不显示。
- **通知**：复用托盘 `showMessage`；只在状态迁移到 `need_input`/`failed` 时发一次；同一 `(sessionKey, status, updatedAt)` 去重；设置可关。
- **停滞**：`lastActivity.at` 超过 `stall_after_min`（默认 5）且 `running` → L0 黄灯，不弹通知；收到新 `step` 自动转回。

### 8.8 打包与安装

- 新增 console 入口 `scripts/af_cli.py`（`af progress ...` / `af mcp`），PyInstaller **onedir** 构建为 `af.exe`，不打包 PyQt5。
- `build_exe.py` 增加 `--with-cli`（或独立 `build_cli.py`），产物放 `dist/af/af.exe`；安装包把它放到 `{app}\af\af.exe`。
- 技能模板里的 `{{AF_CLI}}` 在冻结模式解析为 `{app}\af\af.exe`；源码模式解析为 `.venv\Scripts\python.exe -m agentfloat.services.progress.cli`。
- 不修改系统 PATH；skill 与 MCP 配置都使用绝对路径。
- 启动时 `deploy.py` 检查技能版本/哈希，必要时重写；失败只记日志，不阻塞 AF 启动。

### 8.11 默认取舍（可推翻）

1. **一个 console `af.exe`**，同时提供 `progress` 与 `mcp` 两个子命令；不拆两个 exe。
2. **项目+cwd 单活动会话**为默认解析；`--session` 可选，支持未来多会话。
3. **JSON 沿用 camelCase**，减少从原型迁移的转换成本。
4. **Skill 自动部署到所有已存在的 skills 根**；只写带 `.agentfloat-skill.json` 标记的目录。
5. **MCP 配置只打印、不自动改**；用户在设置页复制，避免再次出现「插件注入」式的侵入感。

### 8.12 风险与护栏

| 风险 | 护栏 |
|---|---|
| CLI 冷启动 >150ms | S1 先计时；超标则改 onedir / 轻量 native shim；不牺牲正确性 |
| CLI/MCP 间接 import PyQt5 | 单测加导入检查；`services/progress` 目录禁止 `PyQt5` 字样 |
| 原子替换后 watcher 丢文件 | 监听目录而非单文件；2s 轮询兜底；文件变更去抖 200ms |
| 覆盖用户已有 skill | `.agentfloat-skill.json` 标记 + 哈希；非本技能目录跳过并提示 |
| MCP 客户端配置摩擦 | `mcp-config` 片段 + 设置页复制；失败自动回退 CLI |
| 并发写冲突 | revision 乐观锁 + 锁文件重试；超时明确报错 |
| need_input 不自动解除 | 收到 step/done 或用户点「继续任务」时清除；失败保留直到新 plan |
