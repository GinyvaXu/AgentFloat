## 0. 方案概览（最终版）

### 0.1 一句话定位

AgentFloat 从「Agent 启动器」升级为「**多 Agent 工作状态中枢**」：用一层环境雷达看全局，用一个独立驾驶舱看细节，回答四个问题——**谁在跑？做到哪？还要多久？谁需要我？**

### 0.2 核心用户时刻与三层价值

- **用户时刻**：同时推进 3+ 个项目（AF / ProjectDock / VIDAR 各一个会话）时，不切换窗口也能掌握全局；需要深看或干预时，再打开工作台。
- **三层价值**：
  1. **可见**：把进度从聊天流里抽出来，变成稳定、可扫视的外部状态。
  2. **可算**：速度投影 + 自适应区间，建立真实的时间感。
  3. **可调度**：把「需要我介入」的会话顶上来，做注意力路由。

### 0.3 形态：三层信息架构（L0 / L1 / L2）

| 层 | 名称 | 何时出现 | 显示什么 | 定位 |
|---|---|---|---|---|
| L0 | 伴生层 | 预计 &gt;2 分钟或 ≥3 步时自动出现；全部结束 10 秒收起 | 每项目一行**标准五件**：项目名 / n/N / 当前步 / ETA / 状态色 | 环境雷达，零点击可见 |
| L1 | 锚定快面板 | 点击 L0 项目条展开，贴浮球 | 当前项目步骤列表、当前步、ETA、失败原因与「需要输入」；承接**中断 / 继续任务 / 聚焦窗口**；不抢焦点 | 轻量查看 + 就地干预 |
| L2 | 独立工作台 | 用户手动 pin 常驻（独立新做） | 主从分栏：左侧项目列表（状态 + n/N + ETA），右侧当前项目完整详情（每步预估 vs 实际、会话信息、操作按钮）；可拖副屏，位置与宽度记忆 | 深度工作与调度 |

- **切换动线**：L0 点项目条 → L1 → 「打开工作台」→ L2；L2 关闭回 L0。不做多入口、不做配置项。
- **排序**：平时按用户固定顺序；等待输入 / 失败 / 完成待验收临时置顶并高亮，处理完回原位。
- **能力来源**：L0/L1 与现有进程面板（`ui/process_panel.py`）**融合**，中断/继续/聚焦等能力下沉，不新增第二个悬停入口；**L2 独立新做**（用户明确选择，偏离「升级进程面板」的推荐）。过渡期需处理旧悬停面板的退役，避免双入口冲突。
- **设计约束**：三层共用同一份状态模型与设计令牌；L2 不复制进程控制逻辑。

### 0.4 数据与协议

- **主通道**：AF 自带 CLI（`af progress …`）+ 自动部署 skill。
  - Agent 执行四个（+1）命令：`plan / step / done / fail`（+ 补充 `need-input`）。
  - 写入 `%APPDATA%/AgentFloat/progress/*.json`（原子写），AF 用 `QFileSystemWatcher` 监听渲染。
  - 跨 Agent：OpenCode / Claude Code / Codex / dsh 等能跑 shell 即可接入；不注入插件、离线可用。
- **契约**（沿用已验证的原型）：
  - 一个任务一份计划，最多 7 步，每步一行 ≤20 字。
  - 状态模型：`project / sessionID / status / steps[{name, etaMin, status, note, startedAt, endedAt, reason}] / current / startedAt / updatedAt / lastActivity / summary`。
  - Agent 自动生成计划，**用户只读**；协议预留 `revision` 字段，编辑能力留到第二阶段。
- **增强与兜底**：
  - 二阶段：精简版 OpenCode 插件（复用归档的 `protocol.ts / state.ts / tool.ts`，去掉显示通道），提供工具级可靠性与 `lastActivity` 停滞检测。
  - 远期：MCP server 作为标准接口。
  - 兜底：只读 `opencode.db` / dsh 状态——零配置降级，拿不到计划与 ETA 时只显示「活跃 / 停滞」，**绝不伪造步骤**。

### 0.5 ETA：算得诚实

- **算法**：**速度投影打底**——用已完成步骤的实际耗时推算全局速度，剩余步骤按 ETA 权重换算，每完成一步重新校准；历史同类步骤统计作为第二阶段增强。
- **健康信号**：`tokens/s` 与 `lastActivity` 只用于「还在不在动 / 是否停滞」，不参与 ETA 计算。
- **呈现**：自适应区间——前 1~3 步给宽区间（如 `~20–60m`），过半后收紧为点估；数据不足显示「待估」，不给假精确。L1 展开显示推算依据，L2 显示每步「预估 vs 实际」。
- **反例记录**：原型中 5 步各 45 分钟 → 标题显示「剩 3h19m」，正是「原始预估累加」被否决的原因。

### 0.6 调度与提醒

- **提醒分级**：
  - 明确上报的**失败 / 需要输入** → 临时置顶 + 托盘通知一次（可在设置关闭）。
  - **推测的停滞**（长时间无活动）→ 仅黄灯 + 一行原因，不弹通知；恢复活动自动转回。
- **项目识别**：项目名默认取 git 仓库根目录名，取不到则用工作目录名；可在 L2 改名（存别名）；重名项目按目录路径 hash 区分。

### 0.7 MVP 台阶（协议闭环优先）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M1 协议闭环** | `af` 四命令 + 状态目录 + 文件监听 + skill 自动部署 + L0 标准五件 + L1 快面板（含中断/继续/聚焦）+ 分级提醒 | OpenCode 里跑 3 个并行任务，L0 实时显示，卡住能就地处理 |
| **M2 独立工作台** | L2 主从分栏 + 每步预估 vs 实际 + 项目别名 + 窗口位置记忆 + pin 常驻 | 多项目场景下，信息与操作不用切窗口 |
| **M3 增强与开放** | 历史速度模型 + OpenCode 精简插件 + 只读兜底 + MCP + 计划模板复用 | ETA 越用越准；其它 Agent 可无痛接入 |

### 0.8 验证与上线节奏

- **试点场景**：OpenCode 单 Agent、多项目日常——用真实工作跑一周（建议 AF / ProjectDock / VIDAR 三会话并行）。
- **成功指标（Round 4 选择）**：
  1. **频率**：≥5 次/天被动扫到 L0、≥1 次/天主动打开 L1/L2。
  2. **信任**：实际完成时间落在 ETA 区间内 ≥70%；最坏偏差 ≤2×。
  - 次要/隔期自评：一周后「关掉它会不会不习惯」；状态汇报类输出字数主观下降。
- **上线节奏（用户自定义）**：debug 版跑通 → 测试版自用 + 持续迭代 → **用户主观觉得很好**后转正式版。默认期间不打 tag / 不发 Release / 不同步官网。

### 0.9 反目标（第一版明确不做）

计划编辑与拖拽排序 · 历史回放与数据看板 · 贴 OpenCode 窗口的像素级进度条 · MCP 与多 Agent 自动接入 · 云同步 · 声音提醒 · 暂停/跳过/重排步骤 · 会话正文入库。

### 0.10 关键风险与对策（速览）

| 风险 | 对策 |
|---|---|
| 三层 UI 各写一套变成三个半成品 | 共用状态模型与令牌；L2 不复制控制逻辑 |
| 旧悬停进程面板与新 L0/L1 双入口 | 明确退役顺序；过渡期避免同时出现两处「运行中」 |
| CLI 每步一次进程启动拖慢节奏 | 轻量入口（目标 &lt;150ms）或常驻管道；必要时转插件通道 |
| 模型漏报导致进度停住 | 停滞检测 + 状态超时降级；不伪造步骤 |
| ETA 假精确破坏信任 | 自适应区间 + 命中率验收；数据不足显示「待估」 |
| 噪音/通知疲劳 | L0 收起态极度克制；只有明确「需要我」才弹通知 |
| 隐私（步骤名含项目/客户信息） | 只存本机、可一键清除、不入库会话正文 |

## 1. 目的与成功标准

- **目的**：为 AgentFloat 设计一个以「Agent 工作进度面板」为核心的新功能/玩法，解决多项目并行时的进度模糊、时间感缺失、状态汇报啰嗦，并提升 AF 的使用频率与不可替代性。
- **本次风暴成功标准**：产出一份**可评审的方案框架**——方向、信息架构、关键取舍、技术路径、MVP 边界与验证指标清楚；不要求执行级排期与代码。
- **节奏**：每轮 2~4 题快问快答 + 自由输入；关节节点给全览；收束由用户手动触发。
- **明确不在本次范围**：直接写代码、改项目源码、排期承诺。

## 2. 初始想法（畅谈整理稿）

> 用户畅谈原文整理（2026-10-19）。

1. **起点**：使用 dsh 时，Agent 有时会出现工作步骤条目，能一栏显示工作现状和后续内容，但仍不够直观。
2. **迁移后的落差**：主要工作平台迁到 OpenCode 后，没有对应的进度插件；尝试自制插件，显示效果很一般。
3. **灵光**：把进度条放到 AgentFloat 上——既升华 AF「Agent 工作站」的概念，又真正解决工作内容模糊、进度模糊的问题。
4. **ADHD 视角**：人在用 Agent 同时推进很多项目时，注意力被分散，无法直观了解 Agent 的工作线路与现状；需要外部化的「工作记忆」。
5. **痛点 1 · 多项目并列**：支持同步推进多个项目的进度并列显示。
6. **痛点 2 · 时间感**：根据 Agent 的 tokens/s 和以往工作经验，推测每个环节大致需要的时间，让多会话控制更有时间概念和规划性。
7. **痛点 3 · 省 token 且更直观**：省去 Agent 在会话里啰嗦项目现状、未来预期的内容；这些内容浪费 token、不直观、充满黑话。希望通过客制化 skills 搭配，把进度汇报搬到 AF，让 Agent 实时操作浮窗上的进度显示面板。
8. **痛点 4 · 产品价值**：丰富 AF 功能，提高使用频率与依赖性。

## 4. 快问快答实录

### Round 1 · 形态与信息层级（2026-10-19）

**Q1 主形态：工作状态层住在哪里？**
- 选项：A 浮球伴生双层 / B 独立悬浮工作台 / C 菜单里的工作台页 / D 贴 OpenCode 窗口
- 回答：**A+B 都要**。A 显示最简单的进度；B 显示最详细的版本；最好能自由灵活切换。
- 结论：不是二选一，而是 **L0 伴生层（A）+ L1 锚定快面板 + L2 独立工作台（B）** 三层。L0 负责环境感知，L2 负责深度查看，L1 是两者之间的点击展开态。

**Q2 出现策略：什么时候出现？**
- 选项：A 值得看才出现 / B 仅多项目时出现 / C 常驻空态 / D 手动 pin
- 回答：**伴生层按 A 自动出现；独立工作台由用户手动 pin。**
- 结论：L0 用「预计 >2 分钟或 ≥3 步」做阈值，全部结束 10 秒收起；L2 不自动弹，由用户固定。

**Q3 收起态信息密度：一行放多少？**
- 选项：A 极简三件 / B 标准五件 / C 数据流七件
- 回答：**B 标准五件。**
- 结论：L0 每行固定「项目名 + n/N + 当前步 + ETA + 状态色」；tokens/s、心跳等放入 L1/L2 或悬停提示。

**Q4 多项目排序：谁在前面？**
- 选项：A 需要我优先 / B 最近活跃优先 / C 用户固定顺序 / D 项目优先级标签
- 回答：**A+C 组合。**
- 结论：默认固定顺序；等待输入 / 失败 / 完成待验收临时置顶并高亮，处理完回原位。

**Round 1 脑洞（待后续验证）**
- 把「进度条」改成「红绿灯」：绿灯在跑、黄灯等你、红灯卡住。
- 不需要你的项目淡出为 3px 呼吸线，只有需要你的项目展开。
- 时间账本：记录 ETA vs 实际耗时，形成个人速度模型。

### Round 2 · 上报通道与 ETA（2026-10-19）

**Q1 上报通道：第一版主通道用哪条？**
- 选项：A CLI + skill / B 精简版 OpenCode 插件 / C MCP server / D 只读会话数据兜底
- 回答：**A CLI + skill 主通道。**
- 结论：AF 自带 `af` 命令并自动把 skill 部署到各 Agent 的 skills 目录；进度写入本地状态目录，AF 文件监听渲染。OpenCode 插件作为二阶段增强，MCP 远期，只读数据只做兜底。

**Q2 上报契约：计划谁定、能不能改？**
- 选项：A 原型四动作、用户只读 / B 首版可编辑 / C 用户先定模板 / D 自动 + 可接管
- 回答：**A 原型四动作，用户只读。**
- 结论：沿用 `plan / step / done / fail / stop`；≤7 步、一行 note；协议预留 `revision` 字段，编辑能力留到第二阶段。

**Q3 ETA 算法：用什么算？**
- 选项：B 速度投影 / B→D 投影 + 历史统计 / A 原始预估累加 / C tokens/s
- 回答：**B 速度投影打底。**
- 结论：用已完成步骤的实际耗时推算全局速度，剩余步骤按 ETA 权重换算；历史统计后置；`tokens/s` 与 `lastActivity` 仅作健康信号。

**Q4 ETA 呈现：怎么显示？**
- 选项：A 自适应区间 / D 分层组合 / B 点估 / C 只报步数
- 回答：**A 自适应区间。**
- 结论：早期宽区间、过半收紧为点估、数据不足显示「待估」；L1 展开显示推算依据，L2 显示每步预估 vs 实际。

**Round 2 关键实证（来自原型与归档）**
- 原型状态模型（本机 `opencode.db` 的 kv 中仍留有 4 组真实记录）：`status / steps[{name, etaMin, status, note, startedAt, endedAt, reason}] / current / startedAt / updatedAt / title / lastActivity / summary`。

### Round 3 · 切换动线、工作台落点与提醒（2026-10-19）

**Q1 三层怎么切换？**
- 选项：A 逐级递进 / B 直达工作台 / C 左键右键分工 / D 完全可配置
- 回答：**A 逐级递进。**
- 结论：L0 点项目条 → L1 快面板 → L1「打开工作台」→ L2；L2 关闭回 L0。不做多入口、不做配置项。

**Q2 L2 工作台建在哪？**
- 选项：A 升级现有进程面板 / B 新建独立工作台 / C 控制与进度分家 / D 只做在 Web 控制台
- 回答：**伴生层和快面板与现有进程面板融合；工作台要做一个独立的。**
- 结论（偏离 Agent 推荐，记录在案）：L0/L1 承接进程面板的「中断 / 继续任务 / 聚焦窗口」能力（能力下沉、不新增悬停入口）；**L2 独立新做**，按驾驶舱标准设计主从分栏窗口。过渡期需处理旧悬停面板的去留，避免双入口冲突。

**Q3 L2 内部怎么排多项目？**
- 选项：A 主从分栏 / B 纵向堆叠卡 / C 看板 / D 焦点模式
- 回答：**A 主从分栏。**
- 结论：左侧项目列表（状态 + n/N + ETA）、右侧当前项目详情（每步预估 vs 实际 + 操作）；窄窗降级与看板留作后续皮肤，一套数据多套渲染。

**Q4 什么时候提醒？**
- 选项：A 分级提醒 / B 只用面板黄灯 / C 全量通知 / D 不检测停滞
- 回答：**A 分级提醒。**
- 结论：明确上报的失败 / 需要输入 → 置顶 + 托盘通知一次（可关）；推测的停滞 → 仅黄灯。协议需补「需要输入」事件。

**Round 3 关键实证与默认项**
- 现有 `ui/process_panel.py` 已具备：卡片、PID、运行时长、最近活动、软中断/结束进程树、继续任务、聚焦窗口、空态、缩放与透明度——L0/L1 的能力下沉有现成实现可复用。

**Round 3 脑洞（待后续验证）**

## 5. 未决问题 · 风险 · 旁支灵感

### 5.1 未决问题（实施期需要定）

- **旧进程面板的退役节奏**：能力下沉到 L0/L1 后，悬停面板何时下线？过渡期如何避免双入口与手势冲突？
- **CLI 形态与性能**：独立轻量 exe 还是复用 Python？目标是启动 &lt;150ms；是否需要常驻管道或本地 HTTP？
- **「需要输入」事件**：作为独立事件还是 fail 的子类型？用户点「继续任务」后如何自动解除？
- **L2 窗口细节**：默认尺寸、位置与宽度记忆、多屏策略、置顶但不抢焦点、缩放与透明度是否沿用进程面板。
- **skill 部署**：自动部署到哪些 Agent 的 skills 目录？与已有 skill（本机约 20 个）的版本更新与冲突如何管理？
- **状态生命周期**：会话结束/中断/崩溃后状态保留多久？多实例与状态目录清理策略？
- **停滞检测阈值**：建议 3–5 分钟起步；是否按任务类型自适应；恢复活动后如何优雅转回。
- **信息分工细节**：L0 的「当前步」摘要由 Agent 上报还是 AF 截断？L2 步骤编辑何时开放（协议已留 revision）。
- **只读兜底**：`opencode.db` 并发读的实现与降级策略；格式变化时的失效保护。
- **历史统计归类**：步骤名如何归类到任务类型（关键词/向量/手动标签）？

### 5.2 风险

- **三层过度设计风险**：L0/L1/L2 各写一套 UI 会变成三个半成品；L2 虽独立新做，但必须共用状态模型与令牌，且不得复制进程控制逻辑。
- **双入口过渡风险**：L0/L1 与旧悬停进程面板并存期间，用户可能看到两处「运行中的 Agent」；需要明确退役顺序。
- **L2 独立新做的工作量**：新窗口、新布局、新交互都要从头验证；MVP 里先只读 + 基础操作，控制范围。
- **噪音风险**：常驻面板变成视觉负担；收起态必须极度克制。
- **假精确风险**：ETA 偏差大破坏信任；用区间/置信度，允许「不估」。
- **协议耦合风险**：显示端只依赖本地状态格式；OpenCode 插件与只读适配器都是可替换的适配层。
- **漏报风险**：CLI 通道依赖模型纪律；用停滞检测与超时降级兜底，不伪造步骤。
- **CLI 开销风险**：每步一次进程启动；需要轻量入口或常驻管道。
- **token 反噬**：上报本身要足够短，否则省下的叙述 token 被吃掉。主价值是可读性而非省 token。
- **隐私风险**：步骤名可能含项目/客户信息；只存本机、可一键清除。
- **性能风险**：多会话高频更新 + Qt 重绘；需要节流、批处理与静息降频。

### 5.3 旁支灵感

- **「需要我」队列**：把「等你输入 / 失败 / 完成待验收」的会话聚成队列，像交通管制一样分配注意力。
- **工作日志自动成稿**：一天结束把各项目步骤流导出为「今日工作摘要」。
- **时间预算**：启动任务前先填「这一步预算 10 分钟」，超时变色，训练时间感。
- **交接模式**：把当前进度面板一键导出为 HANDOFF，供下一个会话/明天接上。
- **历史同类步骤库**：按任务类型沉淀实际耗时，ETA 越用越准。
- **免打扰时段**：专注时收进浮球，只累计「需要我」计数，结束后一次性呈现。
- **每日站会视图**：早上打开 L2，看到昨天遗留 + 今天计划的交接班视图。

### 5.4 待议队列（Round 5 候选）

> 定稿后新增的议题先入队，不打断 M1；等用户说「继续风暴，开任务栏集成」时再逐题讨论。队列按加入顺序编号。

**#1 轻量「进度条」形态 + Windows 任务栏/系统级集成（2026-10-19 加入，用户提出，尚未决定）**

- **用户原话**：「我突然感觉那个进度条的方案也不错，如果可以把类似功能加到 Windows 任务栏或者差不多的地方就更好了，但是我不确定，这个可以加入讨论队列。」
- **议题含义**：除了 L0/L1/L2 这套「浮球系」显示面，再评估一个更轻的形态（单条/极简进度）落在系统级常驻位置——任务栏、托盘、屏幕边缘等。与现有方案不冲突：它是 L0 的替代或补充显示面，M1 协议与数据层可以原样复用。
- **预研备忘（基于已知 Windows API 知识，未联网核实，讨论前建议先做实测）**：

  | # | 路径 | 能做到什么 | 限制 / 成本 |
  |---|---|---|---|
  | 1 | 自家任务栏按钮进度（ITaskbarList3 `SetProgressState` / `SetProgressValue`） | AF 自己的任务栏按钮上原生进度条；可显示聚合进度 | 一个窗口只能一条；无法多项目并列；只在 AF 有任务栏按钮时可见 |
  | 2 | 任务栏按钮角标（`SetOverlayIcon`） | 按钮右下角小角标：需要我 / 失败 / 总数 | 面积很小，只能传达一个状态，不能放文字 |
  | 3 | 托盘图标动态绘制（现有 `QSystemTrayIcon`） | 图标上画环/数字角标，常驻且零占用；点击可展开 L0/L2 | 托盘可能被折叠进溢出区；每帧重绘图标有开销 |
  | 4 | 屏幕边缘 AppBar 停靠条（`SHAppBarMessage`） | 真正的「任务栏旁边一条」：常驻细条、可放多项目行 | 要占用屏幕边缘空间；全屏应用需要自动隐藏处理；属于较重的系统集成 |
  | 5 | 任务栏缩略图工具栏（ThumbBar，悬停按钮弹预览） | 悬停 AF 任务栏按钮时，在缩略图里看状态 + 快捷操作 | 原生只支持按钮（≤7 个），放文字布局要靠自绘窗口取巧，稳定性和工作量都要评估 |
  | 6 | Windows 11 小组件板（Widgets，需要 MSIX 打包 + Widgets SDK） | 离线一瞥的卡片式进度 | 需要打包成 MSIX、另做一套前端；小组件板不是常驻可见面，门槛高 |
  | 7 | 第三方 shell 扩展 / 任务栏改造（DeskBand、注入式方案） | 理论上能把自定义 UI 塞进任务栏 | DeskBand 已废弃、Win11 任务栏不给口子、易随系统更新失效；**不建议** |

- **排进讨论时要回答的问题**：
  1. 这个形态是「替代 L0」还是「与 L0 并存」？若并存，谁是主、谁是镜像？
  2. 任务栏位置只显示聚合（1 条 + 角标），还是想办法做多项目（边缘停靠条 / 缩略图）？
  3. 它服务什么场景：锁屏前扫一眼、全屏工作时可见、还是替代浮球常驻？
  4. 成本收益：与 M2 独立工作台相比，谁的优先级更高？
  5. 是否值得为它牺牲「不占用系统区域、不做注入式改造」这条工程底线？
- **与现有结论的关系**：M1/M2 不受影响；若讨论通过，最可能的做法是把它作为 M3 之后的「显示面扩展」，复用同一套状态 JSON。
