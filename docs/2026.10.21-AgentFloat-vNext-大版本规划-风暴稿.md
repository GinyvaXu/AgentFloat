## 0. 方案概览（当前最优解 · 每轮重写）

### 0.1 一句话

把 AF 从「一个会启动 Agent 的浮球」升级为「**Agent 工作站**」：四条产品线共用一套底座——**Agent Hub（全量 Agent 与安装）· Skill 车间 2.0（发现与安装）· AI 日报 2.0（多源与本地 AI）· 进度面板（多 Agent 状态）**。

### 0.2 四条产品线

| 线 | 名称 | 一句话目标 | 当前状态 |
|---|---|---|---|
| **A** | Agent Hub | 从 4 个内置 Agent 扩展到可安装、可配置、可升级的全量 Agent 中心 | **已定稿**（18+1 冻结 · 分发定稿） |
| **B** | AI 日报 2.0 | 多源、可解释筛选、稳定的本地 AI 总结/分析/翻译 | 方案收口（B2） |
| **C** | Skill 车间 2.0 | 本地 Skill 管理 + GitHub 发现/周榜 + README 预览 + 一键安装 | 方案收口（C2） |
| **D** | 进度面板 | 多 Agent 工作状态中枢（L0/L1/L2 + CLI/skill/MCP） | 方案 v1.5 已定稿，待实施 |

### 0.3 共享底座（四条线不重复造）

1. **Agent Registry**：Agent 能力矩阵、启动预设、版本/安装状态、headless 能力。
2. **Installer Adapters**：npm / pip / winget / 直接下载的统一安装、升级、回滚接口。
3. **Local AI**：headless Agent 调用、prompt 模板、结构化 JSON 校验、总结/翻译/分析。
4. **Source Registry**：资讯源与 GitHub 抓取的注册表、限流、缓存、健康检查。
5. **State & Vault**：进度状态、配置、密钥与环境变量、审计日志。
6. **UI Shell**：Qt 面板族 + Web 控制台 + 托盘/任务栏，共用设计令牌。
7. **Content Catalog（A4 新增）**：远程可更新的内容清单——manifest + 分包 + 签名 + 缓存 + 合并器；首版只服务 Agent 目录，B 的源注册表与 C 的 Skill 索引接同一套。

### 0.4 设计原则

- **先底座后产品线**：A 是 C/D 的前置；B 可并行，但共享 Local AI 与 Source Registry。
- **能力可插拔**：Agent、资讯源、Skill 来源都用注册表，不把新条目写死在代码里。
- **安装必须可回滚**：任何下载/安装/覆盖操作都要有预览、备份、失败回滚。
- **本地优先**：能在本机完成的（总结、翻译、状态）不依赖云；密钥只进 Vault。
- **每一轮可验收**：每条线拆成可独立验收的切片，不做「大爆炸式」重写。

## 2. 现状证据（来自代码与配置）

### 2.1 Agent 侧

- `config.example.json`：内置 3 个 Agent（Claude Code / Codex CLI / Pi Coding Agent），另有 dsh Web 入口；每个 Agent 字段为 `command / args / skip_permissions_arg / working_directory / launch_mode / check`。
- `services/installer.py`：npm 全局安装为主，覆盖 claude / codex / pi / dsh；有镜像回退、版本检测、卸载。
- `core/launcher.py`：支持终端 / Windows Terminal / cmd start / 桌面 App / Web 等启动方式；有 Vault 环境变量注入。
- **缺口**：Agent 数量少、安装方式单一、启动参数没有统一抽象、缺少能力矩阵与健康检查。

### 2.2 AI 日报侧

- `services/news/worker.py`：抓取 → 排序 → 本地 Agent headless 总结 → Markdown；支持 interests 权重、单源重试。
- **缺口**：源覆盖有限；筛选规则偏简单；本地 AI 总结/翻译缺漏没有结构化校验与降级；没有源健康与质量指标。

### 2.3 Skill 车间侧

- **缺口**：没有搜索/发现/安装/更新/卸载；没有 GitHub 来源、周榜、README 预览；没有安装安全与回滚。

### 2.4 进度面板侧

- 已有独立风暴稿 v1.5：L0/L1/L2、CLI+skill+MCP 三件套、速度投影 ETA、M1–M3 切片、试点指标。
- **依赖**：A 的 Agent 元数据、C 的 skill 部署能力。

## 3. 四条线的边界与关键问题

### A · Agent Hub（A1/A2 已完成，A2.5 名单核实完成，方案收口）

**Round A1 结论（2026-10-21）**
- **覆盖边界**：精选 **15–20 个主流 Agent + 自定义入口**；不做字面 50+ 全量，长尾交给自定义与远程目录扩展。
- **安装策略**：**三层适配器**——包管理器优先 → 官方二进制/脚本（校验 + 备份 + 回滚）→ 仅检测（给官方命令）；默认不执行未知脚本。
- **启动参数**：**统一能力模型 + 每 Agent adapter**——interactive / headless / web / desktop / continue / resume 六种模式；高级参数以 key/flag/type/risky 描述。
- **目录更新**：**内置精选目录 + 远程增量 + 用户自定义**；按 `id` 合并，用户本地覆盖优先；离线可用。

**Round A2 结论（2026-10-21）**

- **用户提案**：Agent 更新太快，跟着发版改规范不及时；把规范托管到 Ginyva 工具站，本地核实后上传，AF 打开时自动同步。

- **评估结论**：方向成立，且与 A1 已定的「内置 + 远程增量 + 用户自定义 + 离线可用」一致；但远程目录会下发「要执行的命令」，属供应链面，必须补三道锁：
  1. **签名 + schema 白名单**（Ed25519 公钥内嵌；远程只能覆盖易变层字段；版本单调不回退）；
  2. **失败逐条降级 + 永远有内置兜底**（404/超时→缓存→bundled；schemaVersion 不认→忽略远程；单条非法→只丢该条；用户覆盖优先）；
  3. **发布前 diff 审阅工具**（`af catalog verify`，否则手改 JSON 比发版更慢，方案会退化成"半年更新一次"）。
- **数据分层结论**：稳定层（id/名称/图标/描述）随包内置；**易变层（安装方式/包名/命令名/headless/版本区间/legacy 状态）走远程**；瞬时层（本机版本/登录态/健康）只在本地、永不上传。
- **分发粒度**：`manifest.json`（~2KB，ETag + 24h TTL，启动异步拉）→ 按分组分包（`intl-*.json` / `cn-*.json` / `desktop-*.json`，哈希进文件名）；`minAfVersion` 保护老客户端。
- **发布流水线**：`verify`（并发查 registry，出 diff）→ `review`（overrides.yaml 只改差异）→ `publish --channel beta`（校验 + 签名 + 写 manifest）→ `promote --channel stable`；回滚 = manifest 指回上一版，不动安装包。
- **架构影响**：新增共享底座第 7 块 **Content Catalog**；A 先实现，B 的 `sources.json` 与 C 的 `skill-index.json` 接同一套（避免三套下载器/三种签名）。
- **待定四题**：① 托管组合（Pages+R2+GitHub / 仅 R2 / 仅 GitHub / 自建 API）；② 信任档位（签名 / 仅 schema+HTTPS / 不校验）；③ 刷新策略（异步+分包 / 单文件全量 / 强制同步）；④ 只服务 A 还是三线共用。
